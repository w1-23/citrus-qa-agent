## 1. 引用公平性悖论的破解（本版核心新增）

### 1.1 悖论重述
锁死生成器（四系统同一提示词、要求 `[n]` 引用）后出现新张力：
- 若基线也要求 `[n]` → 等于你给基线"装上了引用能力"，你的引用差异化被稀释；
- 若基线不产生 `[n]` → "引用准确率"对基线无定义，没法比。

### 1.2 破解：把「引用」拆成三个可分离指标

| 指标 | 定义 | 计算 | 比什么 | 基线能否公平测 |
|---|---|---|---|---|
| **① 证据支撑度** (Evidence Support / Groundedness) | 答案中每个原子事实断言，是否被注入证据集合所支撑 | claim 抽取 → 逐 claim 支撑判定（LLM-judge，1/0） | 检索质量 + 生成忠实度 | ✅ 四系统公平（不依赖引用机制） |
| **② 引用存在性** (Citation Existence) | 答案中每个 `[n]` 是否指向一条**真实注入**的证据 | 正则提取 `[n]` → 查证据列表 → 存在性（**全自动**） | **确定性引用过滤的直接效果** | ✅ 基线无过滤 → 会产生不存在的 `[n]` |
| **③ 引用正确性** (Citation Correctness) | 每个存在的 `[n]`，其证据是否**真支撑**它标注的那条断言 | LLM-judge + 人工 κ 子集 | 引用质量（存在但张冠李戴） | ✅ 可测 |

### 1.3 为什么这不是「给基线装引用」
- 锁死生成器要求 `[n]`，是为了让**指标②（引用存在性）对四系统都有定义**——否则基线根本不产生 `[n]`，指标无定义。
- 基线装的是「引用**能力**」，没装「引用**验证**」，所以基线会产生**幻觉引用**（引用不存在的编号）——这正是你的确定性过滤要解决的真实缺陷。
- 因此**独立变量 = 是否有代码级引用过滤**，**因变量 = 引用幻觉率**。干净、可归因，不是拿"功能有无"欺负人。

**论文落点**：§4.3 写「证据支撑度 + 引用幻觉率 + 引用正确性」三张表。核心卖点是：
> *"四系统被同等要求引用；本系统靠代码级过滤使引用幻觉率=0，而通用框架即使被要求引用，仍会引用不存在的编号。"*

## 2. 实验 1 公平基线协议

### 2.1 生成器锁死（复用第一篇 Generator Control Protocol）
- 四系统共用**同一个 LLM 生成器**：同一 `model` + `temperature=0` + 同一套 system prompt（含"用 `[n]` 标注引用、只依据注入证据"）。
- 唯一操纵变量 = 注入的**证据列表**（来自各系统的检索后端）。
- 提示词固定性用**哈希声明**：`sha256(system_prompt)` 跨四系统一致，写进论文。

### 2.2 基线后端双轨制（解"默认配置"歧义）

| 轨 | 定义 | 回答的问题 | 用途 |
|---|---|---|---|
| **轨1 受控对比** | 四系统共享**同一嵌入模型 + 同一分块 + 同一向量库**，只变管道逻辑（编排/精排/阈值/引用过滤/早停） | "是我的**编排**更好，还是模型/语料更好？" | 归因（科学层） |
| **轨2 开箱即用** | LangChain/LlamaIndex 用**默认 embedding + 默认 retriever** | "从业者 pip 装了就用的真实差距有多大？" | 采纳故事（工程层） |

**论文措辞**：轨1 说清楚"唯一自变量是管道逻辑"；轨2 说明"开箱即用"与"增强基线（加 rerank/改写）"两个子档，展示"即使调优也追不上"。

### 2.3 变量控制表（写进 §4.1）

| 变量 | 轨1（受控） | 轨2（开箱） |
|---|---|---|
| 嵌入模型 | 统一 e5-large | 各用默认 |
| 语料分块 | 统一 | 统一（喂相同 chunk 文本） |
| 生成器+提示词 | 锁死 | 锁死 |
| 检索后端逻辑 | **自变量** | 默认 |
| 引用过滤 | 有无（自变量） | 默认无 |
| temperature | 0 | 0 |

## 3. 标注方案与 κ 校验（工作量重估）

### 3.1 不要全人工，复用第一篇「LLM-judge 全量 + 独立校验 κ」模式
- 证据支撑度 / 引用正确性：**LLM-judge 全量打分**（124 题 × 4 系统，逐 claim）。
- 人工只做**验证子集**：随机抽 ~150–200 个 claim，人工独立判定，算 **Cohen's κ / quadratic-weighted κ ≥ 0.8**（对标第一篇 0.812）。
- 这把人工作业量从「1500 句」压到「~200 句 + 抽查」。

### 3.2 标注准则必须写死（否则不可复现）
- **claim 抽取**：明确"一个数字/一个实体关系/一个机制断言 = 一个原子 claim"。
- **支撑判定**：三档 `支撑 / 部分支撑 / 无支撑`，配判例（每条准则附 2 个正例 1 个反例）。
- **引用正确性**：`[n]` 存在且支撑 → 1；存在但错配 → 0；不存在 → 计入②幻觉。

### 3.3 工作量重估（诚实）

| 项 | 量 | 手段 |
|---|---|---|
| 全量 claim 支撑判定 | ~1500 claim | LLM-judge 自动化 |
| 人工 κ 子集 | ~200 claim × 2 人 | 人工，~2–3 天 |
| 引用存在性 | 全自动 | 正则 + 查表，零人工 |

### 4.1 实验 3（边缘部署）收缩到真实可用
- 已有实测：`e6_cpu.json`（CPU p50 embed 2958ms / rerank 2200ms）、`e6_dml.json`（DirectML p50 embed 163ms / rerank 62.2ms）——这是**同机 CPU vs DirectML** 的真实对比。
- **建议**：实验 3 只报「同机 CPU vs DirectML vs（若确有 GPU 再补）GPU」，**不再虚构 RTX 4090 / i5-10400 两台外部机器**。若手头无独立 GPU，就明确写"CPU-only 与 DirectML 两种可用配置"，把 i5 推广站场景用"CPU-only 冷启动"等效表达。
- 冷启动表（15s→2s 等）全部标「待实测」，实测前不进论文。
